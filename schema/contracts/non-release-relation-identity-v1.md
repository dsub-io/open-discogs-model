# Non-release relation identity v1

This contract defines the cross-language identity digest for non-release payload
relations that historically used a signed 32-bit Java hash. The digest is the
semantic identity. The existing `hash` column remains a deterministic
compatibility storage slot during the online transition.

## Canonical digest

The digest is SHA-256 over this byte sequence:

1. UTF-8 bytes of `open-discogs/non-release-relation-identity/v1`, followed by
   one zero byte.
2. The lowercase ASCII relation name, followed by one zero byte.
3. Each field in the relation-specific order below.

Each field is framed independently:

- null: one zero byte;
- value: one byte with value `1`, the UTF-8 byte length as an unsigned 32-bit
  big-endian integer, then the UTF-8 bytes.

Strings have leading and trailing Unicode White_Space code points removed
before framing. The exact set is U+0009-U+000D, U+0020, U+0085, U+00A0,
U+1680, U+2000-U+200A, U+2028-U+2029, U+202F, U+205F, and U+3000. A result
with no code points becomes null. Interior whitespace is unchanged. The owner
ID is constrained separately and is not part of the digest.

| Relation | Owner key | Digest fields in order |
| --- | --- | --- |
| `artist_name_variation` | artist ID | name variation |
| `artist_url` | artist ID | URL |
| `label_url` | label ID | URL |
| `master_video` | master ID | title, description, URL |

An equal digest with a different normalized payload is an error, not an exact
duplicate.

## Compatibility storage slot

The signed 32-bit `hash` column remains the physical unique key with the owner
during transition phase 1. Importers first collapse exact digest duplicates.
Equal digests with different incoming legacy hashes are an error. Within each
owner they reserve every incoming legacy hash, process legacy hash groups in
ascending signed 32-bit order, sort each collided group by unsigned digest
bytes, and retain the legacy hash for the first digest. Each later digest
receives the first unreserved slot generated by attempts starting at zero.

A generated slot is the signed interpretation of the first four big-endian
bytes of SHA-256 over:

1. UTF-8 bytes of `open-discogs/non-release-relation-slot/v1`, followed by one
   zero byte;
2. the lowercase ASCII relation name, followed by one zero byte;
3. the 32 digest bytes;
4. the attempt as an unsigned 32-bit big-endian integer.

A candidate is skipped when it is any row's reserved legacy hash or an already
allocated slot for the same owner. Exhausting all unsigned 32-bit attempts is
an error. Stale reconciliation compares both `identity_sha256` and the allocated
storage slot, so legacy null identities and changed slot assignments are
replaced transactionally.

V021 adds nullable, unindexed digest columns and unvalidated length checks. It
does not scan or rewrite existing relation rows and does not change the existing
`unique (owner, hash)` targets. Artist, Label, and Master contract revision 2
importers reconcile legacy null identities one owner at a time. Old revision 1
progress and successful checkpoints are not compatible with this identity
contract.

## Golden vectors

[`non-release-relation-identity-v1.tsv`](non-release-relation-identity-v1.tsv)
is the machine-readable cross-language test resource. Field values are `null`,
unused (`-`), or `hex:` followed by lowercase UTF-8 bytes. The `Aa` and `BB`
vectors intentionally share Java String hash `2112` while producing distinct
canonical identities. Go and Java model tests consume this same resource;
copied vectors are not authoritative.
