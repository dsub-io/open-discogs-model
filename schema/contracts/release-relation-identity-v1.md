# Release relation identity v1

This contract defines the cross-language identity digest for release relations that historically used a signed 32-bit Java string hash. The digest is the semantic identity. The existing `hash` column remains a compatibility storage slot during the online transition.

## Canonical digest

The digest is SHA-256 over this byte sequence:

1. UTF-8 bytes of `open-discogs/release-relation-identity/v1`, followed by one zero byte.
2. The lowercase ASCII relation name, followed by one zero byte.
3. Each field in the relation-specific order below.

Each field is framed independently:

- null: one zero byte;
- value: one byte with value `1`, the UTF-8 byte length as an unsigned 32-bit big-endian integer, then the UTF-8 bytes.

Strings have leading and trailing Unicode White_Space code points removed before framing. The exact set is U+0009-U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000-U+200A, U+2028-U+2029, U+202F, U+205F, and U+3000. A result with no code points becomes null. Interior whitespace is unchanged. Format quantity is either null or its canonical non-negative base-10 ASCII representation without leading zeroes. The release root ID and the separately constrained scope ID are not part of the digest.

| Relation | Scope key | Digest fields in order |
| --- | --- | --- |
| `credited_artist` | release ID, artist ID | role |
| `format` | release ID | name, reduced description, quantity, text |
| `identifier` | release ID | type, description, value |
| `image` | release ID | file name |
| `track` | release ID | position, title, duration |
| `video` | release ID | title, description, URL |
| `work` | release ID, label ID | work |

For format, `reduced description` preserves source order, removes null and
White_Space-only entries, trims each remaining entry, wraps it as `[d:value]`,
and joins entries with a comma and no additional whitespace. Duplicate entries
are preserved because their source multiplicity is part of the payload.

An equal digest with a different normalized payload is an error, not an exact duplicate.

## Compatibility storage slot

The signed 32-bit `hash` column remains part of the physical unique key in transition phase 1. Importers first collapse exact digest duplicates. Equal digests with different incoming legacy hashes are an error. Within each scope they reserve every incoming legacy hash, process legacy hash groups in ascending signed 32-bit order, sort each collided group by unsigned digest bytes, and retain the legacy hash for the first digest. Each later digest receives the first unreserved slot generated by attempts starting at zero.

A generated slot is the signed interpretation of the first four big-endian bytes of SHA-256 over:

1. UTF-8 bytes of `open-discogs/release-relation-slot/v1`, followed by one zero byte;
2. the lowercase ASCII relation name, followed by one zero byte;
3. the 32 digest bytes;
4. the attempt as an unsigned 32-bit big-endian integer.

A candidate is skipped when it is any row's reserved legacy hash or an already allocated slot in the same scope. Exhausting all unsigned 32-bit attempts is an error. Stale reconciliation compares both `identity_sha256` and the allocated storage slot, so legacy null identities and changed slot assignments are replaced transactionally.

The nullable digest columns make phase 1 a metadata-only schema addition for existing rows. A release import backfills only roots it processes and remains resumable after interruption. A later migration may build partial or concurrent digest indexes after backfill; it must not rewrite or synchronously index the complete catalog in this migration.
